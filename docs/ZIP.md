# ZIP source development (0.3.0)

This describes the ZIP implementation toward 0.3.0. The manifest remains at the last local release, 0.2.0. Registered directories support logical subject/session overlays across ZIP and loose sources, selected member opening, literal metadata previews, and cross-source inheritance through explicit selected-file inspection. Saved custom archive placements are planned for 0.7.0.

## Available now

**BIDS Explorer: Inspect ZIP Archive**, also available on ZIP files in the native Explorer context menu, reads one selected archive's central directory on the workspace host. It accepts an archive anywhere in the filesystem; no dataset descriptor or root-level archive placement is required. The JSON report displays at most 200 members in source order, alongside the total member count, archive URI, size/mtime revision and capture time. Complete coverage means the central directory was enumerated, not that payloads were decompressed, checked or validated as BIDS. It does not register a dataset, infer placement or extract members.

The portable placement model accepts an explicit member-directory prefix and logical dataset-relative destination for each source. Empty prefixes preserve original member roots; wrapper removal is never guessed from an archive's name. It supports whole datasets, subject/session/modality/subtree shards at any physical depth. Duplicate members retain central-directory ordinals as well as archive URI and exact member path. File-wise overlays preserve source choices, merge directories and flag duplicate file paths and file/directory conflicts. The tree uses a dataset-scoped logical overlay, while custom member-root/destination declarations still need a collection editor. Every projected entry retains its original physical source choices. The browser overlays ordinary directory and archive sources, and selected-file metadata inspection uses the same logical ancestors.

## Browsing a ZIP collection

Register the containing directory with **Add Dataset**, or open a BIDS directory with an ordinary root descriptor. The default BIDS tree lays out **dataset → subject → session → modality/processing folder**, overlaying archive and ordinary directory sources. Combined subject/session folders split into logical parents without changing physical paths. Canonical subject/session archive names provide provisional placement within the registered dataset; they do not establish membership across unrelated datasets. Sessions for the same subject are brought together without eagerly indexing their archives. Pipeline namespaces remain separate.

Expanding a session indexes only its contributing ZIPs. An exact matching combined subject/session wrapper, or canonical subject/session wrapper, is removed from navigation after member inspection. Bare subtree shards use their recorded filename placement. Contradictory member subjects/sessions or additional visible entries outside a matching wrapper require explicit placement instead of silently dropping or reassigning content. Directory paths merge file-wise, duplicate files remain individually selectable, and file/directory conflicts stay visible. Source Details retains every original source URI, member path/ordinal and physical relative path beneath `logical.sources`. The display path is never used as a filesystem path.

Unnamed ZIPs can contribute their indexed root entries when their containing branch is expanded, bounded to 32 such indexes per branch; further unnamed archives remain explicit expandable source branches. Arbitrary wrapper mapping and very large custom shard collections still need explicit placement UI and background index orchestration. Derivative processing folders are shown where indexed scientific files support their presence; administrative/unrelated entries remain omitted without modifying them or claiming validation.

Archived JSON/table/gradient/history files use bounded read-only previews, and selected NIfTI files open through the configured viewer after checked extraction. Source Details remains available for every physical choice. Immediate-child coverage describes the projected navigation branch; descendants and unexpanded archives remain unknown. Refresh clears contributing prepared indexes; archive revision changes refuse stale navigation until refresh. The physical adapter retains at most four prepared indexes and 100,000 total member records, separately from completed browser snapshots. Logical branches are bounded to 10,000 contributing sources and 100,000 candidate navigation entries, with cooperative parsing/grouping/publication.

Automatic workspace-root recognition still uses the shallow descriptor check. A descriptorless ZIP collection requires explicit Add Dataset registration (remembered per workspace), or an explicit `bidsExplorer.collectionRoots` workspace declaration listing the workspace-host file URI. Declared roots populate automatically when that workspace opens and are not saved as manual registrations. Root registration declares the exploration scope; archive filenames are provisional placement evidence, not proof that unrelated datasets belong together. The user has explicitly registered UKB_Tractoflow as one collection.

## Reader and bounds

The runtime bundles MIT-licensed `yauzl` 3.4.0 and its `pend` dependency; no Python, shell unzip tool, mount or root access is required. The [upstream reader](https://github.com/thejoshwolfe/yauzl) provides asynchronous lazy central-directory enumeration and ZIP64 support. Tests cover ordinary ZIP records and ZIP64 end records. The index reports all encountered compression/encryption variants; selected-member reading supports only unencrypted stored (method 0) and Deflate (method 8) data: compression methods and encryption flags are recorded, symbolic links and special members are described but never followed, and unsupported/malformed central-directory structures can fail indexing.

- At most 100,000 central-directory records and 16 MiB of accounted directory metadata, including archive comments, fixed records, names, extra fields and member comments. The library can read one bounded record before the cumulative budget rejects it; this is not a total-process memory limit.
- Paths are limited to 4,096 characters and 128 segments. Absolute paths, drive-like paths, traversal, empty/dot segments, backslashes and control characters fail indexing; spelling is not silently repaired. This is index input screening, not a complete future extraction policy.
- Indexing reads the ZIP tail and central records. The tail scan can include incidental compressed payload bytes; no member stream is opened or decompressed. Indexing uses a read-only ordinary-file handle, checks source identity on open and size/mtime/identity before publication, closes the handle on success/failure/cancellation and publishes no partial index. Parent-path races and same-revision replacement remain limitations; this is not a filesystem sandbox or atomic snapshot.
- Cancellation is cooperative between asynchronous central-directory records and before publication. An outstanding filesystem read must finish; no decompressor or worker process runs. Notification cancellation and **Cancel Pending Work** both cancel the inspector.
- The collection model caps declarations at 1,000 sources, visited member records at 100,000 and resulting logical entries at 100,000. It yields during traversal and publication and keeps implicit directories separate from physical member evidence. These are initial conservative limits, not large-cohort support claims.

Selected-member reads now verify CRC and declared/actual output lengths, check source identity/revision, and reject unsupported/encrypted/special members. MRI output is atomically published in a private bounded cache; no whole-archive extraction or shell helper is used. Nested archives inside archive members are not implemented. ZIP files located within ordinary dataset directories are required scope.

On November 5, 2026, an explicitly authorized Rorqual host-side probe used this compiled reader against one ordinary ZIP in the user-supplied collection. The temporary runtime was removed afterward. Only aggregate results are retained in `docs/evidence/0.3.0/zip-index.json`; machine-specific locations remain outside Git. This is a single warm/cold-uncontrolled host measurement, not a cohort benchmark, network-latency measurement or remote VS Code UI test. The rest of the collection was not indexed.

## Archive metadata and MRI opening

The `bids-zip` resource URI identifies the original container, exact decoded member name, central-directory ordinal and captured size/mtime revision. A single URL-safe reference token survives VS Code URI serialization; an extension-host regression tests this boundary. It is an identifier, not encryption or an access-control boundary. Text snapshots also carry explicit container/member provenance for readable source labels. The content provider is readonly and bounded to 1 MiB, with fatal UTF-8 decoding and the existing parser/rendering limits. JSON object fields and top-level array items preserve source order and numeric tokens. Literal array previews do not relax the object requirement for dataset descriptions, dictionaries or inheritance. Duplicate object keys remain literal. Table dictionaries and gradient companions use exact paths in that physical archive; duplicates are ambiguous. The separate **Inspect Metadata** action walks only the selected logical ancestor chain. It applies the existing JSON and diffusion companion rules across loose files and ZIP members, checks the logical dataset/pipeline boundary, and reports incomplete coverage for deferred ZIPs or unavailable branches. Original source links retain ZIP member identity and ordinals. Literal previews keep their existing companion lookup.

Selected MRI members are streamed through size and CRC checks into a fresh private staging directory under VS Code workspace storage on the data host. Payload names use a safe original basename or a fixed `.nii`/`.nii.gz` fallback; member paths never determine destination directories. Unencrypted stored and Deflate data are supported, with a maximum output/input ratio of 1,000 and 512 MiB output per selected member. No inner NIfTI/gzip decoding or BIDS validation is performed by extraction. CRC verifies ZIP payload integrity, not authenticity. Source size/mtime and identity checks detect ordinary changes; same-revision replacement and parent-path races are not fully sandboxed.

Successful output is readonly (0400) beneath a private directory (0700), accompanied by `source.json` provenance, then published through an atomic directory rename. Failures/cancellation close handles and remove partial output; observed cancellation prevents viewer handoff. Core reads fall back to a chunk-sized CRC implementation on older supported Node hosts without native CRC32. No mount, shell archive tool or Python runtime is required.

The cache is bounded per workspace to 2 GiB and 128 artifact directories, with at most one image extraction active in an extension host. Byte accounting includes completed and incomplete artifacts already on disk and provenance overhead. In-memory identical-source reuse rechecks the original archive and cached file attributes; there is no persistent reuse index or automatic eviction. Completed files survive extension reloads so restored viewers keep their resource. **Clear Extracted Image Cache** refuses while archive work or any editor/viewer tabs in the current window remain open. Unexpected cache entries fail closed. A crashed host's partial artifact remains charged to its storage budget until explicit clearing. This is a workspace budget, not a machine-wide quota across independent workspaces.

MRI opening uses ordinary `vscode.open` and the user's configured editor, including NiiVue's supported `niiVue.default` custom editor when selected. No private renderer/webview probes are used by production code. Static inspection of installed NiiVue 2.9.0 confirms that files outside the workspace may be read fully and passed to its webview; extraction does not promise streaming, progressive first frames or reduced voxel memory.

A Remote SSH smoke test displayed an archived 105-volume DWI in NiiVue and previewed a TractoFlow JSON array. In the sampled ZIP, neither of the two gradient input references matched a member path or basename. The archive contained separate pipeline gradient outputs. The preview shows these input references as recorded and does not follow them or attach them to images. Aggregate results and host-side timings are in [archive-viewing.json](evidence/0.3.0/archive-viewing.json).
