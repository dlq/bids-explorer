# Tar reader development

The first 0.4.0 slice adds **BIDS Explorer: Inspect Tar Archive**. It runs on the workspace host using Node streams and zlib. Supported inputs are POSIX ustar `.tar` and gzip-compressed `.tar.gz` or `.tgz`. PAX and GNU extensions, sparse formats, base-256 numeric fields and other compression formats are outside this slice.

The inventory reader scans sequentially and discards member payloads. Gzip requires decompression through the end, including its checksum. The scan caps both source and decoded bytes at 2 GiB and member records at 100,000. It checks header checksums and end records, rejects unsafe paths, retains duplicate member ordinals, and reports links and special entries without following them. Source identity and revision are checked before and after reading. Cancellation tears down the stream and publishes no partial report. These checks do not establish per-member authenticity or BIDS conformance.

Register the directory containing the tarball with **Add Dataset**. The logical tree merges supported tar members with loose and ZIP sources and retains duplicate physical choices. A single top-level directory with one ordinary `dataset_description.json` is shown as the dataset root. **Show Source Details** still reports the full member path and ordinal. Archive names such as `sub-01_ses-01.tgz` use the existing provisional subject/session placement rules.

A branch automatically scans at most one tarball without a subject/session filename hint. Additional tarballs remain expandable by name. An unreadable tarball remains an expandable source so the rest of the branch stays available. Expand that source to see the scan error. Tar file rows use the same JSON, TSV, gradient, history and MRI entry points as ZIP files. **Inspect Metadata** can resolve applicable sidecars across tar, ZIP and loose sources. Raw text opens as a read-only document with the original archive and member identity.

A selected read rescans the archive, checks the exact member ordinal and path, and accepts only ordinary files. It finishes validating the stream and source revision before returning the text or publishing a staged MRI. Gzip integrity is checked at the stream level. Plain tar checks header checksums and payload bounds. Text reads are capped at 1 MiB and MRI reads at 512 MiB per member. MRI files use the shared bounded private cache and open in the configured VS Code viewer. Cancellation or a failed scan discards partial output. Repeat image opens can reuse a completed cache entry, while metadata reads and companion lookups can require multiple sequential scans. [Public smoke fixture](TEST_DATA.md#candidate-tarball-fixture)

The development reader scanned the verified 182,060,400-byte Connectome Mapper fixture and returned all 29 records, including three NIfTI images and the dataset descriptor at the end of the archive. This was a local reader smoke test. The extension-host integration test exercises the command with a synthetic gzip tarball.

The opt-in extension-host test registered the directory containing the real Connectome Mapper tarball. It verified `sub-01 → ses-01 → anat, dwi, func`, confirmed that each MRI row retained its full `ds-sample/` member path, and checked that administrative files stayed out of the logical tree. Set `BIDS_EXPLORER_CONNECTOME_MAPPER_FIXTURE` to the directory containing `ds-sample.tar.gz` when running `npm run test:integration` to repeat this check.

The same opt-in test rendered the dataset description, scan JSON, participants and events tables, and the 129-volume gradient preview in the VS Code extension host. It read the original sidecars through the read-only tar document provider. It also opened all three extracted NIfTI files through VS Code and checked their headers, including the 129 diffusion and 100 resting-state volumes. The test verified viewer handoff and file contents. Rendering in an optional MRI viewer was outside that test.

A local host measurement used an empty BIDS Explorer image cache and the 94,207,537-byte resting-state BOLD member. First materialization took 150.39 ms and a repeat took 0.186 ms. The repeat reused the same cached file. The extracted bytes matched an independent system tar read by SHA-256 and the source archive checksum stayed the same. This single run measures local scan, extraction and cache lookup. Viewer rendering time and Remote SSH performance require separate measurements.
